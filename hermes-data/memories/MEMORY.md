User's preferred "seam" abstraction: bridges ONLY across process boundaries into external runtimes (hermes, OpenClaw, future agents). Never wrap Python stdlib or third-party libraries (`requests`, `urllib`, `subprocess`, etc.) in a seam module - call them directly in the file that needs them. Wrapping library calls "is sensless". The seam lets you swap agent runtimes without touching the rest of the code; it does not exist to hide imports. Concrete instance: `services/agent_bridge.py` in crypto-monitor should expose runtime-bridge functions (e.g. build_daily_report_message that returns text+chart paths for an agent to embed in its response), not Python-lib wrappers.

Crypto-monitor daily publishing model (changed 2026-09-02). Owner's requirement is that every report has an IDENTICAL structure, and an agent composing the post makes it vary run to run - so the pipeline is the orchestrator and the model is a subroutine inside it, never the other way round. Flow: cron fires `crypto-monitor-daily.sh` -> execs `daily_report_pipeline.sh`. The job is `no_agent: true`, so no agent session starts and cron itself delivers nothing - the absent `delivery` block in `/opt/data/cron/jobs.json` is deliberate, do not add one. The pipeline runs collectors + chart generators, asserts the report is fresh and refuses to continue on stale data, then calls `scripts/generate_summaries.py` -> `services/agent_bridge.ask_agent()` -> `hermes -z <prompt> --toolsets context_engine` (one-shot mode, prints only the model's response; `context_engine` resolves to zero tools, so the summariser has no tool surface at all). That is the ONLY place a model is involved. It writes `data/reports/news_summary.md` + `market_summary.md`. Then `scripts/post_to_discord.py` -> `reports.report_builder.build_delivery()` -> `services/agent_bridge.send_message()` -> `hermes send --json --to discord:<channel> <chunk>`. Fixed sequence every run: title, then all 8 charts (`CHART_ORDER`), then the text sections (`SECTION_ORDER`). Charts BEFORE text is a hard owner requirement - he received a report where the graphs arrived last. `MEDIA:<absolute-path>` lines are still the attachment mechanism, but the publisher script emits them, not an agent turn. Credential requirement, this is what makes it work or not: `DISCORD_BOT_TOKEN` must live in `hermes-data/.env`, which every hermes child loads at startup. Hermes strips messaging and provider credentials from the env of any subprocess it spawns, so a compose-only passthrough leaves the child `hermes send` failing with `Platform 'discord' is not configured` - that is exactly how the 10:05 fire on 2026-09-02 died at the publish step. The key IS present in `hermes-data/.env` as of 2026-09-02, but the flow has NOT yet run green end to end, so treat it as unproven until a fire succeeds.

Hermes CLI is at `/opt/data/.local/bin/hermes` inside the container (because HERMES_HOME=/opt/data and `$HOME/.local/bin` resolves there), a symlink to `/opt/hermes/.venv/bin/hermes`. Both are on the image default PATH now, set by `ENV PATH` in Dockerfile.fork. The docker-compose override under `services.gateway.environment` restates the same value: `PATH=/opt/hermes/bin:/opt/pyenv/shims:/opt/pyenv/bin:/opt/hermes/.venv/bin:/opt/data/.local/bin:/usr/local/bin:/usr/bin:/bin`. The ORDER is load-bearing, do not shorten it. `/opt/hermes/bin` must stay first because it holds the `docker exec` privilege-drop shim (`docker/hermes-exec-shim.sh`) that re-execs the real binary as the hermes user - drop it and `docker exec <c> hermes ...` runs as root and leaves root-owned files under /opt/data that the supervised gateway cannot read. The two pyenv entries are the only route to the Python 3.11 (crypto-monitor) and 3.12 (osint) interpreters. Docker compose environment entries REPLACE inherited PATH, not merge - so system paths must be included or basic tools break.
